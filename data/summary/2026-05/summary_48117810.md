這篇 Hacker News 文章的留言主要圍繞著「確定性、完全靜態、無啟發式」的二進制翻譯工具 Elevator 展開，討論了其優勢、效能、技術挑戰及潛在應用。

以下是留言內容的繁體中文總結：

1.  **核心優勢與應用：確定性與認證**
    *   許多留言者認為，該技術最吸引人的地方在於其**確定性 (deterministic)** 和**完全靜態 (fully-static)** 的特性。
    *   這對於**受監管行業**（如航空、醫療設備）至關重要，因為這些行業無法使用 JIT (Just-In-Time) 編譯，需要確保運行代碼與認證代碼完全一致。靜態翻譯能產生可簽署的二進制檔案，為這些領域帶來突破。
    *   有人好奇這類軟體產業的相關性有多高。

2.  **效能表現與比較**
    *   Elevator 據稱能達到與 QEMU 用戶模式 JIT 模擬相當或更好的效能。
    *   然而，多數評論指出 QEMU 的 JIT 是一個「容易擊敗的目標」，因為其設計旨在支援多種架構（TCG），而非針對特定組合進行最佳化，且開發重點在於新架構功能而非速度。
    *   相比之下，Elevator 的效能**顯著慢於 Box64 或 FEX**，但快於 QEMU。

3.  **主要挑戰與限制**
    *   **二進制檔案大小：** Elevator 會導致 `.text` 區段膨脹約 50 倍，這被認為是「巨大的」且可能導致「快取災難」。不過，也有人認為這是實現完全確定性翻譯的合理代價，且實際運行時可能只用到其中一小部分。有建議透過**連結時代碼重排 (link-time code reordering)** 將常用代碼集中，以緩解快取問題。
    *   **間接跳轉 (indirect jumps) 的處理：** 留言者好奇靜態翻譯如何處理間接跳轉。有評論者分享了使用「大型查找表」的業餘解決方案，雖然較慢但通常不影響關鍵效能。
    *   **未支援功能：**
        *   Elevator 目前**不支援多執行緒 (multithreading)** 和**異常處理 (exception handling)**，儘管這些被認為並非不可能實現，只是超出當前專案範圍。
        *   它也**不支援自修改代碼 (self-modifying code)** 或 JIT 編譯代碼，這在文章中已有明確說明，且自修改代碼在現代軟體中已較為罕見。
        *   此外，Elevator 僅支援部分 ISA。
    *   **CPU 狀態與 ABI 模擬：** 該工具需要模擬大量的 x86 CPU 狀態（如 EFLAGS）和複雜的 `mov` 指令，並在呼叫外部時模擬 x86 ABI。
    *   **錯誤處理：** 對於「僅修剪導致異常終止的解釋」的描述，有人澄清這可能意味著將其設定為規範的崩潰處理。

4.  **其他討論**
    *   留言者對其採用的 **Superset CFG (控制流圖)** 概念表示讚賞。
    *   有人提出未來可以引入啟發式方法來修剪可能性空間，以減少二進制檔案大小，儘管這會犧牲確定性保證。
    *   關於**原始碼**的可用性也有人提出疑問。

總體而言，Elevator 提供了一種獨特的、確定性的二進制翻譯方法，尤其適用於對代碼可驗證性有嚴格要求的領域。儘管它在檔案大小和某些功能支援上存在限制，且效能不如某些動態翻譯工具，但其靜態、無啟發式的特性仍被視為一項重要的技術突破。## MetaInfo
