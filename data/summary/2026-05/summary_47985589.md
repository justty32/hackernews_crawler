這篇 Hacker News 文章關於版本控制三十年歷史的留言，主要圍繞著對 Git 替代方案的討論、對舊系統的懷念與其優缺點、以及 Git 在當前生態系統中的主導地位。

以下是留言內容的繁體中文總結：

1.  **對 Mercurial (Hg) 的懷念與 Bitbucket 的轉變：**
    *   許多留言者對 Mercurial 懷有懷舊之情，惋惜 Bitbucket 終止支援的決定，並認為這並未對 Bitbucket 帶來顯著好處。
    *   他們特別懷念 Mercurial 的簡潔性以及在 Windows 上與 TortoiseHg 的良好整合。

    *   有人因此轉向 Sourcehut 等平台，並認為 Atlassian 不適合單人開發者。
    *   儘管有新的替代方案如 `jj`，但其指令的晦澀程度被認為與 Git 無異，未能解決根本問題。

2.  **Subversion (SVN) 的擁護者與其優缺點：**
    *   部分留言者仍是 Subversion 的忠實用戶，特別是對於單人專案或包含大量大型二進位檔案的專案，認為 SVN 在處理這些方面優於 Git（即使搭配 Git LFS 也被視為「半成品」的解決方案）。
    *   他們非常喜歡 SVN 簡單、線性遞增的全球版本號，認為這比 Git 的雜湊值更易於人類理解。
    *   有人指出，GitHub 的流行諷刺地將開發流程重新中心化，這正是 SVN 的一個特點。
    *   然而，SVN 的缺點包括無處不在的 `.svn` 目錄令人困擾，以及其中心化模式（儘管現代 SVN 已引入「changelists」實現本地提交，但普及度不高且客戶端支援有限）。
    *   SVN 的開發也顯著放緩，儘管它在某些特定場景下仍被認為是最佳選擇。

3.  **早期專有系統與先進功能：**
    *   留言者回憶起 1980 年代末至 1990 年代初的專有系統，如 Apollo Computer 的 DSEE（後來的 Clearcase）。
    *   這些系統與檔案系統深度整合，版本控制（提交、分支）運作方式類似 ZFS 快照，允許用戶直接「cd」到任何標籤、分支或提交版本而無需檢出，被認為是非常酷且希望現今仍有的功能。
    *   然而，Clearcase 在管理上出了名的複雜，需要專職管理員才能維持運作。

4.  **Fossil 作為 Git 替代方案：**
    *   Fossil 被提及為一個可行的替代方案，因其整合了維基、論壇、問題追蹤等功能而受到讚揚。
    *   它在處理二進位檔案方面也被認為優於 Git。
    *   但其普及受限於 Git 生態系統的主導地位，許多開發工具和工作流程都已針對 Git 進行優化。

5.  **版本控制的歷史演進與遷移：**
    *   有留言者分享了他們的主儲存庫從 RCS 經 CVS 最終遷移到 Git 的經驗，歷史可追溯至 1985 年，且每次遷移都是無損的。
    *   文章也提及了分時系統中版本化檔案作為版本控制的早期形式，例如 Donald Knuth 的 Tex 目錄。

6.  **對 Git 的看法與「更好的 Git」的渴望：**
    *   儘管 Git 佔據主導地位，但其複雜性、晦澀的指令以及對大型二進位檔案處理不佳等問題仍被提及。
    *   許多人渴望一個「更好的 Git」或替代方案，能提供更簡單的工作流程、更好的二進位檔案處理，或更易於人類閱讀的版本控制（如線性數字）。
